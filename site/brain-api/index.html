Brain API 协议

四个端点、一组固定字段、一套正文内文本约定。

本文对应仓库里的 docs/brain-api-spec.md，是客户端（人类侧）与 agent 侧实现的完整契约。所有状态按 brain_id 隔离，并由服务端持有。

传输

项约定
方法四个端点一律 POST，无查询参数
鉴权Authorization: Bearer <token>，四个端点都要求（流式同理）。服务端 token 为空字符串表示不启用鉴权，此时客户端不发送这个头
请求体编码application/msgpack 或 application/json，各端点支持范围见下表
成功响应编码与请求体编码相同；/brain-to-human 恒为 MessagePack 帧流
失败响应非 2xx + Content-Type: text/plain，正文为一句人类可读的原因
音色可选请求头 x-brain-voice（旧名 x-might-voice 也认）。两个提交端点都接受，只有 /agent-to-brain 上的会影响合成，且只作用于那一条消息
  • 成功响应的 Content-Type 绝不为 text/plain。客户端的成功/失败判据只有这一条。
  • 请求体必须是对象（map / object），不是数组或标量。未知字段一律忽略。

端点总览

端点方向语义请求编码响应编码
POST /human-to-brain人类 → brain提交，等待转写仅 MessagePackMessagePack
POST /brain-to-humanbrain → 人类长轮询，分帧流仅 MessagePackMessagePack 帧流
POST /agent-to-brainagent → brain提交，立即返回MessagePack / JSON同请求编码
POST /brain-to-agentbrain → agent长轮询MessagePack / JSON同请求编码

agent 那一对的编码判定：Content-Type 为 application/json 时按 JSON 解析，其余（含缺省）按 MessagePack 解析；响应使用同一编码。人类那一对只按 MessagePack 解析，Content-Type 不参与判定。

POST /human-to-brain

提交一段人类语音，返回转写文本。阻塞至转写完成。

// 请求（MessagePack）
{
  brain_id: string,               // 必填，非空
  audio: Uint8Array,              // 必填，非空；Ogg Opus 16 kHz 单声道
  unheard_text?: string | null,   // 可选，打断时没听完的那段
}

// 响应（MessagePack）
{ kind: "text", text: string }

返回的 text 是转写结果；它的文本形态同时进入给 agent 的流。转写超时或上游失败返回 502。

POST /brain-to-human

长轮询，取 brain 对人类的回复。响应是分帧流：一条回复拆成若干帧，合成出一段就吐一段。

// 请求（MessagePack）
{ brain_id: string, skip_before?: number }

// 响应（MessagePack 帧流）
[u32 大端长度][MessagePack]   ← 一帧，重复 N 次

// 每帧：
{ kind: "text", text: string, sentences: string[], skipped: boolean }           // 每条消息的第一帧
{ kind: "text", text: string, audio: Uint8Array, consumed_sentences: number }   // 音频帧
{ kind: "failed", consumed_sentences: number }                                  // 合成中途失败
{ kind: "empty" }                                                               // 等到超时、没有内容
  • 第一帧不带音频：text 是整条原始文本（<!-- disable voice --> 段照原样保留），sentences 是 wtpsplit 的句子表（它的 join 不一定等于 text）。客户端可以先上屏。
  • 之后每帧是"这一块念的文本 + 音频 + 累计消费的句子数"。被打断时用 consumed_sentences 算还剩几句没听到。
  • skipped: true：客户端 skip_before 跳过的旧消息，只有文本帧、没有音频，sentences 为空数组。一条响应里可以有零到多条 skipped 帧，后面再跟真正的回复——读完整条 body。
  • { kind: "failed", consumed_sentences }：合成中途挂了。正常说完不会有这一帧。
  • 整条都被静音时只有第一帧，没有音频帧。
  • audio 是 Ogg Opus，每帧是一个独立的文件：按帧解码，把 PCM 追加到播放队列，不要字节拼接。
  • skip_before（可选，UTC epoch 毫秒，客户端的钟）：早于这个时刻入队的 agent 消息不合成、不丢弃，而是以 skipped: true 的文本帧回给客户端，由它决定显示、忽略还是记进 unheard_text。
  • 客户端断开，服务端立即停止后续合成；已经取走的这条消息不会重投。
没有 final 字段。body 正常结束 = 说完了。怎么切块不在协议里：客户端只该假设 "第一帧的文本是整条回复，音频按序拼起来就是整条语音"。

POST /agent-to-brain

agent 提交一段文本。该文本会被合成语音并经 /brain-to-human 交付给人类。

// 请求（MessagePack 或 JSON）
{ brain_id: string, text: string }   // text 必填，非空

// 响应（同请求编码）
{ kind: "empty" }

立即返回，不等待合成。text 允许包含静音标记（见文本约定）。x-brain-voice 头只作用于这一条消息；不带就用部署方配的默认音色。brain 上不存音色。

POST /brain-to-agent

长轮询，取 brain 交付给 agent 的文本。

// 请求（MessagePack 或 JSON）
{ brain_id: string }

// 响应（同请求编码）
{ kind: "empty" }
| { kind: "text", text: string }

text 的取值按产生来源分：

来源正文形态
人类语音转写<asr-recognized-text>…</asr-recognized-text>
人类打断时的补充<unheard_text …>…</unheard_text> 前置
服务端校对告警<asr-warning>…</asr-warning>

帧流细节

/brain-to-human 的响应永远是一串帧，没有"单个 MessagePack"的形态：

while (true) {
  read 4 bytes -> length (big-endian u32)
  read length bytes -> MessagePack
  if (kind == "empty") break        // 超时，没有内容，立刻重发
  if (frame.audio) enqueue(frame.audio)   // 每帧是独立的 Ogg 文件，各自解码
}
// body 正常结束 = 这一条说完了
  • 读法：不靠 MessagePack 自己定界——各语言的流式 unpacker 支持参差，而"读 4 字节、再读 N 字节"谁都会写。
  • 截断：读不到完整的一帧（连接中断、长度越界）= 这条丢了。客户端重新发起请求即可，服务端不会重投。
  • 超时语义：超时只约束等第一帧（默认 25 秒）。开始吐帧之后，这条连接可以一直挂到说完。一帧都没有就发一帧 { kind: "empty" } 收尾。
  • 首帧（只有文本和句子表）几乎立刻到；第一块音频通常在一两秒内跟上，不需要等整条合成完就开始播。

brain_id

  • 由用户配置的字符串，客户端手输，形如 "员工3"、"my-brain"。长度 1–64 字符。
  • 不要求预先登记。服务端第一次见到某个 brain_id 时创建它。没有"没有这个 brain"这条失败路径，也不存在 404；拼错名字的后果是开了一段新对话，不是报错。
  • 所有会话状态（历史、队列）按 brain_id 隔离。
  • 状态在内存里，空闲 2 小时后被卸载。卸载或重启都等于那段对话没了。客户端要自己把 brain_id 稳定住，并接受长期空闲后上下文丢失。

正文内的文本约定

以下字符串属于接口契约，标记为逐字匹配。

转写与回复

<asr-recognized-text>…</asr-recognized-text>：人类语音的转写，交付给 agent。<agent-response>…</agent-response>：agent 提交文本的回显形态。多行内容时标签内部两侧各有一个换行，内容两端空白被去除；单行时标签紧贴内容。

校对告警

<asr-warning>…</asr-warning>：服务端对转写可能不准确的提醒，混在给 agent 的流里交付。客户端无需解析。

打断补充

/human-to-brain 的 unheard_text 为人类打断时未听到的内容。可空：缺省、null、空串均视为本次无内容。非空时前置到该次转写之前，一并交付给 agent：

<unheard_text reason="用户打断讲话">
第一句没听完
</unheard_text>
<asr-recognized-text>帮我把客厅的灯关一下。</asr-recognized-text>

语音禁用标记

/agent-to-brain 的 text 内可用下列标记划定不合成语音的区段：

第一句要念。<!-- disable voice -->此段不合成。<!-- enable voice -->第三句要念。
  • 两个标记之间的内容（含标记本身）不进入语音合成；text 本身不受影响，人类侧仍显示完整文本。
  • 一条 text 内可出现多组。标记不成对时，开区间自标记处延续至文本末尾。
  • 整段均处于禁用状态时，该条不产生语音：/brain-to-human 里只会有一帧 { kind: "text", text }。

音频

方向字段编码采样率
上行/human-to-brain 请求的 audioOgg Opus16 kHz
下行/brain-to-human 响应的 audioOgg Opus不保证（见下）
  • 音频在 MessagePack 中为 bin 类型，非 base64。
  • 下行音频由 TTS 端点产出，服务端原样透传、不做重采样；它只是"碰巧"通常是 24 kHz，客户端不得依赖这个值。
  • Opus 内部恒为 48 kHz；Ogg Opus 头里的采样率只是提示信息。客户端解码器（如 Android 的 MediaCodec）通常直接输出 48 kHz。客户端必须读解码器实际输出的采样率再据此重采样，不得写死。

投递语义

  • /brain-to-human 与 /brain-to-agent 为长轮询。收到 { "kind": "empty" } 表示当前无内容，客户端应立即重新发起请求，不得等待或退避。
  • 消息读即消费：服务端取出后即从队列移除，无确认、无重投。响应未能送达客户端即视为该条丢失；回复中断时同理，已发出的帧算送达。
  • 队列有上限（当前两个方向各 64 条）。达到上限时丢弃最旧的一条。
  • 每个 brain_id 的每个出向队列只应由一个消费者轮询。多个消费者会各自取走一部分消息。
  • 失败一律通过 HTTP 状态码表达。协议层不定义错误消息体，也不存在表示错误的 kind。401 不应重试。

超时

项当前值说明
/human-to-brain13 s转写上限，超时返回 502
/brain-to-agent25 s长轮询上限，超时返回 empty
/brain-to-human25 s只约束等第一帧；开始吐帧后可以挂到说完

上述值为服务端默认，可配置（MIGHT_BRAINS_POLL_TIMEOUT_MS）。客户端应把长轮询上限视为"服务端可能长时间不返回"。

错误码

码含义
200成功
400请求体形状或编码不合法
401鉴权失败
500服务端内部失败
502上游失败（转写 / 分句 / 合成）

错误体一律 text/plain，绝不能长得像那个端点的成功响应——否则会被客户端当成一条合法回复去解。
